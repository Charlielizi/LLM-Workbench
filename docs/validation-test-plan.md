# AIHub 完整验证测试计划

版本：1.0
适用基线：AIHub `0.1.x`，Electron 桌面端为主，Windows Native 客户端为独立验证对象
最后更新：2026-07-22
配套记录：[validation-test-run-template.md](./validation-test-run-template.md)
AI 无人值守 UI 专项：[ai-autonomous-ui-validation-plan.md](./ai-autonomous-ui-validation-plan.md)
供应商专项：[provider-web-regression-checklist.md](./provider-web-regression-checklist.md)

## 1. 目的与质量目标

本计划用于回答四个发布问题：

1. AIHub 的本地会话、消息、组织、知识、迁移和设置能力是否正确且不会丢数据。
2. 七个供应商网站变化、登录状态、网络波动或页面虚拟化时，发送链路是否可恢复、可诊断且不会串会话。
3. Electron 的 IPC、浏览器隔离、外部导航和富内容渲染是否守住安全边界。
4. Windows 安装包能否在干净环境安装、升级、卸载并保留用户数据。

发布质量目标：

- 不丢失已完成的用户消息、助手消息、设置或会话组织信息。
- 不把 A 会话或 A 供应商的事件写入 B 会话。
- 不出现供应商网页已经完成回复而 AIHub 长期无结果且无法诊断或恢复的情况。
- 不泄露登录 Cookie、API Key、用户文件内容或敏感诊断数据。
- 所有对外宣称“支持”的供应商都具备登录后的真实端到端证据。
- 安装包与源码基线一致，自动化门禁全部通过，可回滚到上一个可用版本。

## 2. 范围

### 2.1 本轮必须验证

- Electron 桌面端：主进程、preload、renderer、Provider WebContentsView、SQLite。
- 七个供应商：ChatGPT、Claude、豆包、Kimi、DeepSeek、腾讯元宝、千问。
- 三种后端模式：`web`、`manual`、OpenAI-compatible `api`。
- 会话与消息：创建、发送、流式、取消、删除、编辑重发、搜索、置顶、重命名、删除。
- 网站历史同步、供应商会话 URL 绑定、后台发送、回复重同步、熔断恢复、Clean Mode。
- 富内容：Markdown、代码、公式、图片、引用、供应商 HTML、安全清理。
- 文件夹、标签、批量操作、会话导入导出、设置导入导出。
- 系统提示词、本地知识文档、检索上下文、跨供应商迁移、对比会话。
- IPC 输入验证、来源隔离、权限拒绝、外部链接、敏感信息脱敏。
- Windows Squirrel 打包、干净安装、覆盖升级、卸载、数据保留。
- `apps/windows-native` 的构建、单元测试和最小实站冒烟；其发布结论与 Electron 分开。

### 2.2 条件验证

- macOS：只有在本里程碑声明支持时，执行 Electron 源码运行与核心 P0 用例；当前 Windows 安装包门禁不由 macOS 结果替代。
- 附件、模式和模型选择：仅对运行时明确发现能力且 UI 暴露控制的供应商执行正向门禁；其余供应商验证“不误显示、不误操作”。
- Windows 10：仅在发布支持矩阵明确包含它时成为发布门禁，否则记录为兼容性观察项。

### 2.3 不在范围内

- 绕过验证码、登录验证、地区限制或供应商风控。
- 调用供应商私有 API、导出认证 Cookie、对供应商服务本身做负载测试。
- 比较模型答案事实质量；本计划只验证传输、归属、完整性、状态与渲染。
- Electron 与 Windows Native 的完整功能一致性；两者当前是独立产品面。

## 3. 基线、术语与测试标记

每次执行必须固定并记录：

- Git commit、分支和 `git status --short`；脏工作树需保存 diff 摘要。
- `pnpm-lock.yaml` 哈希、Node、pnpm、Electron、Windows/WebView2 版本。
- 测试构建类型：`dev`、`packaged`、`installed`、`upgrade`。
- 应用 `userData` 目录、诊断目录和运行时 `instanceId`。
- 各供应商账号状态，但记录中不得出现账号、Cookie、Token 或 API Key 明文。

优先级：

- `P0`：发布阻断；核心路径、数据、安全、安装或支持供应商正常发送。
- `P1`：高价值回归；失败会明显影响可用性，但存在可接受的临时规避路径。
- `P2`：兼容性、外观或低频边界；可带经批准的已知问题发布。

执行类型：

- `A`：仓库中已有自动化覆盖。
- `A+M`：自动化验证逻辑，仍需真实 UI 或实站证据。
- `A*`：应补充自动化，目前不能依赖人工长期兜底。
- `A*+M`：既要补自动化，也必须保留真实 UI 或实站验证。
- `M`：人工或实站验证。
- `AI`：由 Electron/浏览器自动化执行真实交互，并由 DOM、几何、截图和业务状态联合判定。

结果只能使用：

- `Pass`：全部预期满足且证据完整。
- `Fail`：可复现地违反预期。
- `Blocked`：外部条件阻止执行，例如账号验证；不能计入通过率。
- `Not Run`：尚未执行。
- `N/A`：经测试负责人确认，本构建不提供该能力。

### 3.1 角色与责任

| 角色 | 责任 |
|---|---|
| 开发负责人 | 冻结代码基线、提供可重复构建、解释警告、修复缺陷并给出影响范围 |
| 测试负责人 | 维护范围与优先级、分配环境、审核证据、计算通过率和提出 Go/No-Go 建议 |
| 供应商验证人 | 准备合规测试账号、执行实站矩阵、保存脱敏诊断；不得绕过供应商验证 |
| 安全审核人 | 审核 IPC、外链、HTML、日志、导出和秘密管理用例及证据脱敏 |
| 发布负责人 | 确认安装包哈希、升级/回滚、缺陷豁免、支持声明和最终发布决定 |

同一人可以兼任多个角色，但 P0 豁免和最终发布决定至少需要测试负责人、发布负责人共同确认。

## 4. 风险模型与验证重点

| 风险 | 可能后果 | 重点检测 | 门禁 |
|---|---|---|---|
| 供应商 DOM 漂移 | 无法输入、提交或抓取回复 | Fixture、实站矩阵、诊断快照 | P0 |
| 锚点或事件串线 | 抓到旧回复、重复回复、写错会话 | 切换会话、并发供应商、虚拟列表 | P0 |
| 完成判断过早/过晚 | 截断答案或永久 streaming | 网络、停止按钮、文本稳定窗口 | P0 |
| SQLite 迁移或级联错误 | 用户数据丢失/孤儿记录 | 旧库升级、崩溃恢复、导入导出 | P0 |
| IPC/HTML 注入 | 本机代码执行、数据外泄 | Schema fuzz、XSS、外链协议 | P0 |
| 登录会话未隔离 | 账号串用、隐私泄露 | Partition/Cookie 隔离 | P0 |
| 后台视图生命周期错误 | 隐藏后不回复、资源泄漏 | 后台发送、反复开关、长稳测试 | P1 |
| 安装包与源码不一致 | 用户无法安装或运行 | 干净机安装、升级、签名/版本检查 | P0 |
| 编码损坏 | 中文内容不可读 | 中英混排、emoji、历史坏编码样本 | P1 |

## 5. 测试环境矩阵

### 5.1 必需环境

| 环境 | 用途 | 最低执行集 |
|---|---|---|
| E1：Windows 11 x64 开发机 | 自动化、调试、实站主回归 | 全部自动化、P0/P1 功能、七供应商 |
| E2：Windows 11 x64 干净用户/虚拟机 | 安装与首次启动 | PKG 全套、APP P0、两家供应商冒烟 |
| E3：Windows 11 x64 升级环境 | 上一版本升级 | 旧库迁移、设置与登录持久化、回滚 |
| E4：Windows 11 非管理员标准用户 | 权限边界 | 安装/启动、文件选择、诊断、卸载 |
| E5：Windows Native + WebView2 | Native 独立验证 | Native 自动化、启动、一个真实供应商 |

若发布支持其他 Windows 版本或 macOS，新增环境而不是替代 E1–E4。

### 5.2 显示与输入组合

- 分辨率：1280×720、1920×1080、2560×1440。
- 缩放：100%、125%、150%；至少一轮多显示器切换。
- 主题：亮色、暗色、跟随系统。
- 输入：中文 IME、英文、emoji、组合字符、粘贴多行文本。
- 网络：正常、低速/高延迟、发送中短时断网、离线启动、恢复联网。

### 5.3 供应商账号状态

每个供应商至少准备以下可复现状态中的前两种：

1. 已登录且可连续发送。
2. 未登录或会话过期。
3. 需要验证码/二次验证。
4. 限流或配额不足（只能自然出现，不主动施压）。

账号受阻时用例记为 `Blocked`；正确识别 `auth_required` 只证明错误处理，不证明该供应商发送能力通过。

## 6. 测试数据

### 6.1 标准提示词集

| 数据 ID | 内容特征 | 用途 |
|---|---|---|
| TD-01 | `只回复：AIHUB-SMOKE-<timestamp>` | 唯一性、重复与串线检查 |
| TD-02 | 中文、English、emoji：`你好 AIHub 🌏 café` | Unicode 与编码 |
| TD-03 | 要求输出标题、列表、表格、代码块 | Markdown/代码渲染 |
| TD-04 | 要求输出行内公式和块公式 | KaTeX/MathJax 抽取 |
| TD-05 | 要求分 20 点逐步生成 | 慢流式、取消、完成检测 |
| TD-06 | 含 `<img onerror=...>`、`javascript:` 链接 | HTML/XSS 安全；不得执行 |
| TD-07 | 100,000 字符边界及 100,001 字符越界 | IPC 边界；越界必须拒绝 |
| TD-08 | 仅空格、空文本、仅附件 | 输入约束 |
| TD-09 | 同一句发送到 2–4 家供应商 | 对比会话一致性 |
| TD-10 | 包含前文唯一事实的 10+ 轮会话 | 搜索、迁移、知识与锚点 |

### 6.2 文件集

- 有效小文件：PNG/JPEG、PDF、DOCX、XLSX、PPTX、TXT，各一个。
- Unicode 文件名、空格文件名、超长文件名。
- 0 字节文件、已删除路径、无读取权限文件。
- 500 MB 边界与超过 500 MB 文件；单次 20 个与 21 个附件。
- 包含提示注入文本的知识文档，用于确认上下文边界而非执行本机行为。

真实供应商附件上传只使用无敏感信息的合成文件。

### 6.3 数据库集

- 空白库。
- 上一发布版本创建并包含会话、消息片段、HTML、设置、文件夹、标签、提示词和对比会话的库。
- 10,000 个会话、100,000 条消息的性能库。
- 发送过程中强制退出后留下 `pending/streaming` 状态的恢复库。
- 备份副本上的损坏库，用于验证失败可诊断；不得破坏唯一用户数据。

## 7. 执行层级与标准命令

### 7.1 L0：基线与静态门禁

```powershell
git status --short
git rev-parse HEAD
pnpm install --frozen-lockfile
pnpm typecheck
```

通过条件：依赖安装可重复、TypeScript 全工作区无错误、不产生未解释的锁文件变化。

### 7.2 L1：TypeScript 自动化

```powershell
pnpm test
```

覆盖 `@aihub/core`、`@aihub/adapters` 和 `@aihub/desktop`。不得只运行单个测试文件作为发布证据。当前重点套件包括：

- Core：transfer、system prompt、retrieval、message content。
- Adapters：definitions、provider overrides、conversation URL。
- Desktop：AppService、database、IPC schemas、ProviderRuntime、provider preload、WebsiteAdapter、富内容、安全清理、smoke tooling、renderer 关键行为。

### 7.3 L2：Windows Native 自动化

```powershell
.\.dotnet\dotnet.exe test .\apps\AIHub.Windows.sln --configuration Release
```

若仓库内 SDK 不存在，改用已固定版本的 `dotnet` 并记录版本。

### 7.4 L3：开发构建与 Fixture 集成

```powershell
pnpm --filter @aihub/desktop start
```

使用仓库 Fixture 验证 DOM 抽取、锚点、网络空闲、鉴权阻断、Clean Mode 和虚拟列表。Fixture 通过不能替代真实供应商验证。

### 7.5 L4：真实供应商冒烟

应用保持运行时顺序执行：

```powershell
pnpm smoke:matrix
pnpm smoke:summary
```

专项场景：

```powershell
pnpm smoke:provider -- -Provider doubao -Scenario manual-recovery
pnpm smoke:provider -- -Provider doubao -Scenario resync-latest
pnpm smoke:provider -- -Provider doubao -Scenario background-send
```

使用 `pnpm smoke:watch` 等待对应结果。结果必须匹配当前 `runtime.instanceId`；旧实例或旧时间戳结果无效。

### 7.6 L5：打包与安装

```powershell
pnpm --filter @aihub/desktop package
```

保存 `AIHub-Setup.exe`、SHA-256、大小、生成时间、commit 和完整构建日志。随后在 E2/E3 执行 PKG 用例。

### 7.7 推荐执行顺序

`L0 → L1 → L2 → L3 → 数据功能 → 供应商实站 → 安全 → 稳定性/性能 → L5 安装升级 → 发布评审`。

前一层出现 P0 失败时暂停昂贵的全矩阵实站测试，但仍需保存失败证据。

### 7.8 执行频率

| 触发点 | 必跑内容 |
|---|---|
| 每个合并请求 | L0、L1；改动 Native 时增加 L2 |
| Provider adapter/preload/runtime 改动 | L0–L3、受影响供应商 PVD-02/03/05/08、一个未改供应商对照组 |
| Database/schema/import 改动 | DATA 全套、ORG-07/08、升级 Fixture、安装升级 |
| IPC/security/content 改动 | SEC 全套、CNT-04、恶意导入集 |
| 每周或 DOM 漂移告警后 | 七供应商正常 smoke matrix 和结果趋势汇总 |
| 每个 Release Candidate | 本计划全部 P0/P1、安装升级、60 分钟 soak |
| 正式发布前 | 复核缺陷、支持矩阵、包哈希、签字和回滚资产 |

### 7.9 AI 无人值守 UI 模式

本计划中的 `M` 表示当前实现状态仍需要人工，并不表示长期接受人工兜底。界面显示与交互应按 [AI 无人值守 UI 与交互验证计划](./ai-autonomous-ui-validation-plan.md) 逐步转换为 `AI`：

- 通过 Electron 自动化执行真实 click、keyboard、drag、scroll，而不是直接调用组件 handler。
- 每个关键页面同时验证 DOM、bounding box、截图和 IPC/数据库状态。
- 使用可控 Mock Provider 自动制造慢流、失败、登录阻断、重同步和后台生成。
- 已有登录 session 的真实供应商由 AI 顺序执行；验证码只记 `Blocked` 并继续，不等待用户。
- 最终目标命令为 `pnpm test:ai`；在该命令真正实现前，不能宣称 UI 测试已完全无人值守。

## 8. 准入与退出标准

### 8.1 测试准入

- 产品范围和本次支持的供应商/系统版本已明确。
- 所有计划提交已进入同一基线，或脏工作树 diff 已冻结存档。
- `pnpm install --frozen-lockfile`、`pnpm typecheck` 和 `pnpm test` 通过。
- E1 可启动，诊断目录可写，实站账号与合成数据可用。
- 上一版本安装包和数据库备份可用于升级测试。

### 8.2 发布退出

- P0：100% `Pass`；`Blocked` 不算通过。
- P1：至少 95% `Pass`，其余必须有负责人、规避方案和批准的发布豁免。
- 无未关闭的 S0/S1 缺陷；无数据丢失、安全泄露、跨会话串线缺陷。
- 所有本版本宣称支持的供应商通过 PVD-01～PVD-10；若不能通过，必须从支持声明降级并在 UI/发布说明中明确。
- Windows 干净安装、升级和卸载通过；安装包哈希与测试包一致。
- 60 分钟稳定性测试无崩溃、无永久卡流、无超过基线 20% 的持续内存增长。
- 测试记录、诊断、截图、日志、缺陷和最终签字完整。

## 9. 详细验证用例

下面的步骤是最低要求。执行人可增加观察点，但不能删除 P0 预期。

### 9.1 构建、启动与生命周期

| ID | P | 类型 | 场景与步骤 | 通过标准 |
|---|---|---|---|---|
| GATE-01 | P0 | A | 冻结锁文件安装；运行全量 typecheck/test | 命令退出码 0；无锁文件漂移；警告已解释 |
| GATE-02 | P0 | A+M | 运行开发构建，观察 bootstrap 日志 | 主窗口可交互；无未处理异常；运行实例信息生成 |
| APP-01 | P0 | M | 清空测试 userData 后首次启动并完成 onboarding | 首屏、默认供应商和设置正确；重启不重复 onboarding |
| APP-02 | P0 | M | 连续启动第二个 AIHub 实例 | 只保留一个主实例；已有窗口被恢复/聚焦；数据目录无竞争损坏 |
| APP-03 | P0 | M | 创建会话并发送，正常关闭后重启 | 已完成数据完整；窗口恢复可用；供应商登录会话仍隔离持久化 |
| APP-04 | P0 | M | 流式中关闭应用，再次启动 | 不崩溃；旧流不会继续写错会话；非终态有明确失败/恢复表现 |
| APP-05 | P1 | M | 最小化、恢复、切换显示器、休眠唤醒 | 布局不丢失；ProviderView 不覆盖错误区域；恢复后可发送 |
| APP-06 | P1 | M | 快速打开/关闭设置、迁移、对比、提示词弹窗 | 无遮罩残留、焦点陷阱或状态串扰 |

### 9.2 会话与消息

| ID | P | 类型 | 场景与步骤 | 通过标准 |
|---|---|---|---|---|
| MSG-01 | P0 | A+M | 为每家供应商创建新会话 | provider 归属正确；标题和时间正确；选择态唯一 |
| MSG-02 | P0 | A+M | 发送 TD-01，观察全部状态阶段 | 用户消息与唯一助手消息最终 completed；正文与网页一致 |
| MSG-03 | P0 | A+M | 使用 TD-05，流式中取消 | 生成停止或进入明确终态；部分文本不重复；可继续发送 |

## 10. 自动化覆盖缺口与实施顺序

现有自动化对 Provider pipeline、数据库底层和 schema 边界覆盖较强，但以下能力需要补齐，避免每次发布完全依赖人工：

1. `P0`：为所有 IPC handler 建立参数化 schema/副作用拒绝测试，而不只验证 schema 对象。
2. `P0`：上一版本数据库 Fixture 升级、崩溃遗留状态和导入原子性测试。
3. `P0`：会话 JSON 导入导出往返、恶意 HTML/URL/路径输入测试。
4. `P0`：对比会话的部分失败、并发归属和重启恢复测试。
5. `P0`：迁移确认失败、压缩失败和批量迁移幂等测试。
6. `P1`：Renderer 级搜索、置顶、文件夹、标签、批量操作、快捷键和弹窗焦点测试。
7. `P1`：系统提示词优先级、文档关联隔离、删除引用和检索注入边界测试。
8. `P1`：本地受控 SSE 服务覆盖 API 分片、断流、超时、4xx/5xx 和取消。
9. `P1`：安装包启动 smoke，验证三个 preload bundle 和 asar 资源存在。
10. `P2`：视觉截图基线和 DPI/主题组合回归。

补测完成后，将表格中的 `A*` 改为 `A`，并在本文件记录对应测试文件；不要仅修改标记而没有可运行证据。

## 11. 缺陷分级与处置

| 严重度 | 定义 | 示例 | 发布处理 |
|---|---|---|---|
| S0 | 安全事故或不可恢复的大范围数据损失 | Cookie/API Key 泄露、数据库被清空 | 立即停止测试和发布 |
| S1 | 核心功能不可用或数据/会话串线 | 回复写错会话、支持供应商无法发送 | 必须修复并全量回归 |
| S2 | 高价值功能失败但有明确规避 | 手动恢复不可用、某富内容错误 | 修复或书面豁免 |
| S3 | 低影响显示/易用性问题 | 个别 DPI 截断 | 可纳入已知问题 |

每个缺陷至少包含：用例 ID、环境、commit、时间、复现率、最小步骤、预期/实际、截图、日志、provider diagnostics、runtime instanceId、是否含敏感信息、首次坏版本和修复验证范围。

修复后执行：失败用例 → 同模块 P0/P1 → 相邻数据/安全用例 → 受影响供应商矩阵。涉及 Provider preload、AppService、database 或 IPC 的修复必须重新跑 `pnpm typecheck` 和 `pnpm test` 全量。
